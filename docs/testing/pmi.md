# Программа и методика испытаний

Система переводов «Aqsha». Структура документа — по ГОСТ 19.301-79 «Программа и методика испытаний. Требования к содержанию и оформлению»; виды испытаний — с учётом ГОСТ 34.603-92.

## 1. Объект испытаний

1.1. Наименование: система переводов денежных средств «Aqsha» (далее — система).

1.2. Состав:
- сервис платежей `payments` — приём переводов по gRPC, хранение их статусов;
- сервис счетов `ledger` — счета, балансы, проведение переводов;
- брокер сообщений Apache Kafka — передача событий между сервисами;
- СУБД PostgreSQL — отдельная база для каждого сервиса.

1.3. Версия: текущая версия ветки `main`; номер коммита фиксируется в протоколе испытаний.

## 2. Цель испытаний

Проверить, что система выполняет переводы корректно и ровно один раз, в том числе при сбоях отдельных компонентов, и соответствует требованиям раздела 3.

## 3. Требования к программе

| № | Требование |
| --- | --- |
| ТР-01 | Сервис платежей принимает запросы только с действующим ключом клиента (`x-api-key`); без ключа — код `UNAUTHENTICATED` |
| ТР-02 | Сумма перевода — целое число тиынов от 1 до 100 000 000 000 включительно; иначе — `INVALID_ARGUMENT` |
| ТР-03 | Перевод на тот же счёт отклоняется с кодом `INVALID_ARGUMENT` |
| ТР-04 | Повтор запроса с тем же ключом идемпотентности возвращает тот же перевод и заголовок `idempotent-replayed: true`; второй перевод не создаётся |
| ТР-05 | Повтор ключа идемпотентности с другими параметрами отклоняется с кодом `ALREADY_EXISTS` |
| ТР-06 | Перевод выполняется асинхронно: ответ — статус `PENDING`, итог — `COMPLETED` или `FAILED` с причиной |
| ТР-07 | При недостатке средств перевод завершается `FAILED` с причиной `insufficient_funds`, балансы не меняются |
| ТР-08 | Баланс счёта не может стать отрицательным, в том числе при одновременных переводах |
| ТР-09 | Повторная доставка события о переводе не изменяет балансы повторно |
| ТР-10 | Итоговый статус перевода не изменяется последующими событиями |
| ТР-11 | При недоступности сервиса счетов переводы не теряются и завершаются после его восстановления |
| ТР-12 | При недоступности Kafka события сохраняются и отправляются после её восстановления |
| ТР-13 | Событие, которое невозможно обработать, помещается в очередь недоставленных сообщений (DLQ) и не останавливает обработку остальных |
| ТР-14 | Клиент видит только свои переводы; чужой перевод — код `NOT_FOUND` |
| ТР-15 | Изменения gRPC-контрактов обратно совместимы с предыдущей версией |
| ТР-16 | Под нагрузкой 20 одновременных клиентов 95 % запросов на перевод выполняются быстрее 300 мс, доля ошибок — меньше 1 %, сумма балансов всех счетов не изменяется |

## 4. Требования к программной документации

Предъявляются: README с описанием запуска, контракты gRPC (`proto/`), [тест-стратегия](test-strategy.md), настоящая программа и методика, [протокол испытаний](protocol.md).

## 5. Средства и порядок испытаний

5.1. Технические средства: среда GitHub Actions (Ubuntu 24.04, 4 vCPU, 16 ГБ ОЗУ) или рабочая станция с Docker.

5.2. Программные средства: Go 1.24, Docker Compose, kind, PostgreSQL 17, Apache Kafka 3.9.1, k6, buf.

5.3. Порядок испытаний:
1. Проверка контрактов и статический анализ (задание CI «Контракты»).
2. Автономные испытания компонентов: юнит, интеграционные и системные тесты (задание «Тесты»).
3. Комплексные испытания в Docker Compose: E2E, хаос-тест, нагрузка (задание «E2E»).
4. Испытания развёртывания в Kubernetes (задание «Kubernetes»).

Каждый этап начинается только после успешного завершения предыдущих 1–2. Результаты фиксируются в протоколе.
