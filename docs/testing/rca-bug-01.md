# Разбор дефекта BUG-01: сервис стартовал без таблиц

## Что случилось

Первый прогон интеграционных тестов сервиса счетов: упала большая часть тестов. Сервис отвечал `INTERNAL` на открытие счёта, в логе:

```
level=ERROR msg="ошибка базы" err="ERROR: relation \"accounts\" does not exist (SQLSTATE 42P01)"
```

При этом миграции «прошли» без ошибок — `Migrate` вернул `nil`.

## Как искал причину

1. **Таблицы нет в тестовой базе.** Значит, либо миграции не запускались, либо применились не туда.
2. **Шаблонная база чистая.** `\dt` в `template1` пуст — таблица `schema_migrations` не могла «приехать» из шаблона и пометить миграции применёнными.
3. **Миграции не нашлись.** Файлы встроены в бинарник директивой `//go:embed migrations/*.sql`. Встроенная файловая система хранит их с путём `migrations/001_init.sql`, а `Migrate` искал `*.sql` в корне — и получал пустой список. Пустой список — не ошибка, поэтому функция честно ничего не делала и возвращала успех.

## Причина

Корневая — **молчаливый успех на пустом входе**. Функция, которая должна изменить схему базы, не считала «нечего применять» подозрительным. В продакшене это выглядело бы так: сервис стартует, проходит проверку здоровья, а каждый запрос получает `500`.

## Исправление

- `Migrations()` возвращает подкаталог `migrations` через `fs.Sub` — пути совпадают с тем, что ищет `Migrate`.
- `Migrate` возвращает ошибку «нет файлов миграций», если список пуст: сервис не стартует, и это сразу видно.

## Как не допустить повторения

- Тест `TestMigrateErrors` проверяет оба случая: пустой набор — ошибка; упавшая миграция не отмечается применённой.
- Тест `TestMigrateOnceUnderConcurrency` проверяет, что пять одновременных запусков применяют каждую миграцию один раз — так стартуют несколько реплик в Kubernetes.

## Как искать такие проблемы на стенде

У каждого запроса есть `trace_id`: он приходит в ответе gRPC (`x-request-id`), пишется в лог каждого сервиса и передаётся в заголовках Kafka. По одному идентификатору видна вся цепочка перевода:

```
$ grep '"trace_id":"k6-3-12"' payments.log ledger.log
00:41:29.429 payments  grpc            CreateTransfer code=OK
00:41:29.429 payments  перевод принят  transfer_id=f91a2b47-…
00:41:29.507 ledger    перевод обработан  result=completed
00:41:29.529 payments  перевод завершён   status=completed
```

Если перевод завис в `pending`, по той же цепочке видно, на каком шаге он остановился: событие не ушло из outbox (растёт метрика `aqsha_outbox_unsent`), не обработано сервисом счетов или итог не вернулся.
